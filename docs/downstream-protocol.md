# 下游 WebSocket 协议

`server` 默认监听 `ws://127.0.0.1:8080/ws`，通过 `BRIDGE_LISTEN` 修改。
只有 `/ws` 接受升级；其他路径返回 HTTP 404。当前没有独立服务访问 token，
默认回环监听，使用主播身份码订阅。客户端示例见
[downstream_client.rs](../crates/bridge-native/src/bin/downstream_client.rs) 和 [README](../README.md#下游客户端示例)。

## 接入与兼容

握手后 10 秒内发送一次 JSON 文本订阅；每条连接只订阅一个房间，换房间需重新连接。
身份码去掉首尾空白后必须非空，房间号不能替代身份码。身份码不放在 URL 中，
响应不返回身份码、平台 Access Key 或鉴权正文。

原实时模式保持兼容：

```json
{"type":"subscribe","code":"主播身份码"}
```

返回 `{"type":"ready","room_id":123,"game_id":"场次 ID"}`，再发送原格式事件。
不要求 ACK，不补发历史；落后于 256 条广播缓冲时收到 `lagged` 并继续。
订阅后发送其他业务文本消息（包括 ACK）会被拒绝。

确认模式首次订阅：

```json
{"type":"subscribe","code":"主播身份码","ack":true}
```

从加入时的实时位置开始，不回放加入前的事件。返回：

```json
{"type":"ready","room_id":123,"game_id":"场次 ID","stream_id":"流标识","seq":120,"resumed":false,"ack_window":64}
```

`seq` 是本次接入起点，下一条事件为 121；首次场次尚无事件时为 0。
起点与日志快照同时确定，取得订阅和发送 ready 期间的新事件仍可读取。
`ready` 必定先于本连接的事件。

首次开启的 HTTP 请求最多等待 10 秒，每个上游候选地址分别有 10 秒连接及鉴权超时，
接入没有额外总超时。取得场次后即维护项目心跳，心跳失效或退出中止建连并清理场次。

## 事件与累计 ACK

确认模式的事件添加流标识与桥侧序号，保留 `room_id / cmd / data`：

```json
{"type":"event","room_id":123,"stream_id":"流标识","seq":121,"cmd":"LIVE_OPEN_PLATFORM_DM","data":{"msg":"你好"}}
```

`stream_id` 是进程内该事件流的随机标识；原场次上游恢复保持不变，重新开启的场次使用新标识。
`seq` 从 1 递增，是 u64 JSON 整数；超出 JavaScript 安全整数范围的客户端须使用无损整数解析。
它只标识桥成功记录的事件，无法判断上游没有到达桥的事件数量。
已知事件 data 使用 Rust 结构序列化，包含默认字段，未声明字段会忽略；
未知命令保留原始 data，缺失时为 null。客户端应容忍未知命令、消息类型和新增字段。

客户端在业务处理成功后发送累计 ACK：

```json
{"type":"ack","stream_id":"流标识","seq":125}
```

表示已经连续处理完截至 125 的所有事件，不是仅确认收到某一帧。
允许重复确认相同位置；拒绝回退、跨流或超过当前连接已开始发送位置的确认。
ACK 只用于当前连接的流量控制；客户端负责保存已处理游标，并在重连请求中带回。
服务端没有持久化客户端身份或 ACK，也不因某个客户端 ACK 就删除共享历史。

最多允许 `ack_window` 条未确认事件。窗口满时暂停业务事件，继续处理 ACK、Ping/Pong 和状态；
ACK 推进后继续从日志读取。订阅可额外提交正整数 `ack_window`，实际窗口取请求值与服务配置的较小者，
ready 返回实际值。示例请求 64，使窗口不超过本地有界处理队列。
客户端网络读取应与业务处理分开，避免处理耗时导致 Pong 超时。

处理完成但 ACK 丢失可能造成重复交付。客户端应按 `(stream_id, seq)` 去重；
需要跨客户端重启恢复时，应将业务结果和游标一起持久化，不能仅依靠 WebSocket 发送成功。

## 游标续传与保留范围

断线后重新连接，用相同身份码提交最后连续处理完成的位置：

```json
{"type":"subscribe","code":"主播身份码","ack":true,"resume_after":{"stream_id":"流标识","seq":125}}
```

成功后 ready 返回 `resumed:true` 和请求的 seq，从 126 顺序补发到实时尾部。
历史和实时使用同一读取游标，不设置另一个切换队列。
续传必须启用 ack。续传只查询现有日志，不会因为游标不存在而调用 start 或换到新场次。
身份码必须曾被成功接入并关联该流；每条流最多保留最近 128 个身份码指纹，
身份码不匹配与流不存在使用相同错误，避免暴露其他房间的日志范围。

每个 Manager 及其克隆共享有界内存日志，默认：

| 限制 | 默认值 | 配置 |
| --- | --- | --- |
| 事件和结束流保留时间 | 300 秒 | `BRIDGE_EVENT_RETENTION_SECS` |
| 全部流的事件字节预算 | 32 MiB | `BRIDGE_EVENT_LOG_MAX_BYTES` |
| 活动与结束流数量 | 128 | `BRIDGE_EVENT_LOG_MAX_STREAMS` |
| 每条连接 ACK 窗口 | 64 条 | `BRIDGE_ACK_WINDOW` |

全部限制必须为正整数。字节预算计入记录 JSON、命令和固定记录开销；
流元数据、旧实时广播、客户端与传输缓冲和临时序列化内存另计，不代表进程 RSS 上限。
按事件写入时间过期，容量不足时跨流淘汰最早记录；保留范围以两者先到达者为准。
单条事件超过整个字节预算时不能保存，推进序号并清空该流此前日志，以形成明确缺口。
流数量满时优先淘汰最早结束流；全部流均活动时拒绝新场次接入并清理其平台场次。
时间过期在访问日志时清理；等待 ACK 的连接也会在日志变化或心跳周期检查缺口。

无法完整续传时返回以下消息，并用关闭码 1008 关闭，不静默跳到最新位置：

```json
{"type":"resume_unavailable","reason":"cursor_expired","earliest_after":130,"latest_seq":200}
```

| reason | 含义 |
| --- | --- |
| `stream_unavailable` | 流不存在、已淘汰、桥重启，或身份码未关联；范围字段为 null |
| `cursor_expired` | 下一个应读事件或未确认事件已被淘汰 |
| `cursor_ahead` | 游标超过已记录尾部 |

`earliest_after` 是当前允许提交的最小 resume_after.seq；不是第一条事件的序号。
发生缺口后，客户端应停止并由业务决定是否放弃完整性、重新从实时位置订阅。
示例不会自动降级；确认模式不发送 lagged。

## 上游生命周期与结束回放

`server` 在最后一个订阅者离开后保留上游 30 秒，期间继续记录事件和维护两类心跳。
上游保活时间与日志保留时间独立；会话结束后保留日志，续传可以补完尾部，再收到 closed。
日志期限内回放结束流不重新开启平台场次。结束流的事件仍受各自写入时间和容量限制。

`LIVE_OPEN_PLATFORM_INTERACTION_END` 作为最后事件记录。确认模式在尾部读完且全部发送事件
得到 ACK 后发送 closed；原实时模式仍转发后直接结束。
普通 `LIVE_OPEN_PLATFORM_LIVE_END` 只转发，不结束订阅。
服务主动退出会通知 closed 并清理，不等待全部业务 ACK；进程退出后内存日志失效。
因此停机、进程重启和保留范围外不提供恢复保证。

上游断线、发送超时（默认 5 秒）或 60 秒无有效活动时，默认在 120 秒内恢复原场次，
保留订阅、流标识、桥侧序号和项目心跳，发送 status：

```json
{"type":"status","state":"reconnecting"}
{"type":"status","state":"connected"}
```

首次正常接入由 ready 表示，不额外发送初始 connected；恢复期间加入先 ready 再 reconnecting。
状态按最新快照发送，中间变化可以合并。恢复通知优先于恢复后事件。
上游恢复空窗没有补发，不保证全部 B 站事件到达桥，暂不跨上游连接去重。
鉴权拒绝、协议/业务解码错误、恢复预算耗尽、闲置到期、项目心跳终止或退出都会结束会话。
项目心跳暂时失败按默认 45 秒预算恢复，不额外发送 status。

## 资源保护与暂时错误

第一阶段不要求注册、登录或服务 token，只使用主播身份码。server 自身不部署 TLS 或反向代理，
不按 IP 分配额度。所有网络连接、Manager 克隆和进程内接入共享同一个 ResourceBudget。

| 资源 | 默认上限 | 覆盖范围 |
| --- | --- | --- |
| 下游连接 | 512 | 握手、等待订阅、已订阅，直至连接任务结束 |
| HTTP→WS 握手 | 32 | 升级成功、失败或超时后释放 |
| 待接入请求 | 64 | 等待共享结果的每个请求，包括进程内接入 |
| 开场任务 | 4 | 平台 start、上游连接与鉴权，含失败后的必要清理 |
| 上游会话 | 64 | 建立、活动与清理；已结束日志不占名额 |
| start 频率 | 1 次/秒、突发 2 | 实际 start 调用；失败也消耗 |
| 每房间订阅 | 32 | 活动网络与进程内订阅；活动续传不能绕过 |
| 每连接业务消息 | 1000 次/秒、突发 2000 | Subscribe、ACK 和其他文本/二进制业务帧，在 JSON 解析前检查 |

这些是工程默认值，不是平台官方配额；配置名见 README 和 .env.example。
资源不足快速拒绝，不排无界队列。已知会话复用不消耗 start 配额；未知身份码即使可能映射已有房间，
也必须先通过新场次准入。跨码合并在重复场次结束后归还多占的开场和会话名额。

停止等待立即释放待接入名额，不 abort 共享开场任务；后台任务继续持有开场及场次清理责任。
这些预算不参与项目心跳、原场次上游恢复及 end 的准入，不能阻止已有会话保活和关闭。
活动流续传受房间订阅上限约束，额度不足不能降级为无守卫回放；已结束流的只读回放不占上游会话名额。

暂时错误仍使用 type=error，增加稳定 code 和可选建议延迟：

```json
{"type":"error","code":"server_busy","message":"资源额度暂不可用，请稍后重试","retry_after_ms":1000}
```

| code | 含义 |
| --- | --- |
| server_busy | 连接、握手、待接入、开场或会话额度不足 |
| rate_limited | 实际 start 或本连接业务消息超过频率 |
| subscription_limit | 同房间的活动订阅已达到上限 |

WS 暂时拒绝随后用 1013 关闭；retry_after_ms 仅是重试建议，不保证届时可用。
字段缺失时客户端仍可指数退避并加入抖动。重试应保留已处理游标，不自动改为全新实时订阅。
旧客户端仍可解析 type=error、code 和 message；若不认识新增 code，可按普通错误结束连接，
支持自动恢复的新客户端需识别这三个暂时错误。清理中暂不能加入的会话返回 server_busy，稍后可按原游标重试。
重复 ACK 不推进确认位置、不触发重复唤醒，但每条仍计入入站消息额度。
控制帧不计入业务消息频率；一旦超额，连接结束，不继续解析超额业务消息。

升级前若资源允许回应，使用 HTTP 503 与 Retry-After（整数秒）；否则允许直接断开。
拒绝路径不创建额外异步任务。示例对 HTTP 429/503、上述三个暂时 WS 错误重试，
处理缺少 retry_after_ms 的响应；实际等待为基础退避与建议的较大者，加 0–20% 抖动。
远端建议最多采纳一天，避免异常值造成定时器溢出。

## 错误、保活和退出

所有业务消息使用 JSON 文本帧：ready、event、status、lagged（实时模式）、
resume_unavailable（确认模式）、error 和 closed。
原有 error.code 保持含义：invalid_request（首包、重复订阅或 ACK 无效，关闭码 1008）
和 attach_failed（平台开启或接入失败，关闭码 1011）。这些错误与 resume_unavailable
需要检查配置或由业务决定处理，不自动放弃历史完整性重试。具体平台错误记录在服务端日志。
closed 使用关闭码 1000。读写故障或连接已断开时可能直接断开，不能依赖最后一定收到消息。

服务端持续读取控制帧并自动回复 Ping；ready 后每 20 秒发送标准 WebSocket Ping，
10 秒内未收到相同负载的 Pong 时断开。主动或旧 Pong 不解除新 Ping 的超时。
客户端使用 WebSocket 库的控制帧处理能力即可，不需要 JSON 心跳。
握手、首包和单次发送最多等待 10 秒，客户端单帧和完整消息最多 8 KiB。

Ctrl-C 或 Unix SIGTERM 停止接入、通知下游关闭，并等待共享开场与会话结束请求完成。
待接入请求可以取消等待，共享任务不因单个请求退出而丢弃已发出的平台开启请求。
发送字节预算、历史回放限速和失败身份码冷却不在此阶段实现。


## HTTP 接入协议（为 Worker 适配预留）

core 定义 `downstream::admission`，native 的 `downstream_client` 已支持此协议。
当前 native `server` 仍只提供原有 `/ws`，尚未实现 HTTP 接入服务或 Room DO。

客户端向配置的完整 HTTP(S) 接入地址发送 POST，Content-Type 为 application/json。
正文与 subscribe 的订阅参数相同，但不含 `type`：

```json
{"code":"主播身份码","ack":true,"ack_window":64,"resume_after":{"stream_id":"原流标识","seq":125}}
```

首次接入省略 `resume_after` 或设为 null。HTTP 与 WebSocket 共用身份码、ACK 窗口和续传校验。
携带游标时只查找旧流，不得因旧流不可用而开启新场次。成功返回 HTTP 200：

```json
{"websocket_url":"wss://bridge.example/ws?ticket=opaque-ticket","expires_in_ms":30000}
```

`websocket_url` 是含短期不透明凭证的完整地址，不得包含主播身份码；日志不得记录完整 URL。
`expires_in_ms` 是从服务端生成响应起的有效毫秒数，必须为正。示例客户端保守扣除整个 HTTP 请求耗时，
并将升级期限限制在剩余有效期内。HTTPS 接入只接受 WSS 地址，不跟随 HTTP 重定向，响应正文最多 8 KiB。
客户端只应配置可信的接入服务；返回的 WebSocket 可以位于不同主机。

凭证应绑定授权、订阅参数、目标房间/流及有效期，服务端在升级时验证并登记订阅。
客户端连接该地址后不再发送 subscribe，也不再发送身份码；收到 ready 才表示订阅成功。
HTTP 接入到 WebSocket 建连之间的预留资源由服务端租约负责回收。

失败使用非 2xx 状态及与 WebSocket 相同的 `error` 或 `resume_unavailable` JSON 正文。
`error` 包含 code、message、可选 retry_after_ms；`resume_unavailable` 包含 reason、earliest_after、latest_seq。
建议参数错误用 400、授权错误用 403、续传失败用 409、限流用 429、暂时繁忙用 503。
示例客户端优先解释业务错误：server_busy、rate_limited、subscription_limit 可重试；续传失败及其他业务错误终止。
无有效业务错误正文时，HTTP 429 和 5xx 重试，其他状态终止；有效 200 响应以外的成功状态视为协议错误。
HTTP Retry-After 支持整数秒，与正文建议同时存在时取较大值。原有退避上限和抖动规则保持不变。

每次重连都携带最新已处理游标重新 POST，不能复用旧凭证或自动清除游标。
Room WebSocket 升级以 401 或 410 表示凭证无效/过期时，客户端重新接入；403 等其他终止性拒绝不重试。
接入 POST、升级和发送分别最多等待 10 秒，Ctrl-C 可以取消接入请求及退避。

### 应用层保活

无法主动发送标准 WebSocket Ping 的服务端可发送：

```json
{"type":"ping","nonce":"本次探测标识"}
```

客户端立即原样应答：

```json
{"type":"pong","nonce":"本次探测标识"}
```

nonce 为不超过 256 UTF-8 字节的字符串。服务端每次使用新的标识，只接受与当前探测匹配的 pong。
建议 ready 后每 20 秒探测、10 秒未匹配即断开；接入等待中也可以发送 ping。
保活不推进业务游标、不占 ACK 窗口，不使用 status 消息代替。
native 示例客户端支持两种保活，业务处理不阻塞应答；90 秒没有任何入站帧则重连，发送 ACK 不延长该期限。
native server 继续使用标准控制帧，不主动发送应用层 ping，也不接受未经请求的应用层 pong。
