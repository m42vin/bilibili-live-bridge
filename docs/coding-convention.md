# 编码规范

本文约定新增和实质修改代码的组织、注释与测试方式。存量代码随改随补，不为满足本文发起批量格式整理或测试迁移。
模块职责和运行时约束见 [架构说明](architecture.md)，开发与验证步骤见 [开发指南](development.md)，对外消息契约见 [下游客户端协议](downstream-protocol.md)。

## 通用

- 新写或实质修改的注释使用中文；代码标识、协议字段、方法名、日志字段和文件路径保留原文。
- 注释说明用途、原因、边界与不变量，不复述签名中的类型，不记录实现流水账或修改历史。
- 公开接口、行为、配置与对应文档在同一次修改中更新；过期注释按缺陷处理，不用 TODO 代替同步维护。
- 示例、测试与文档使用假凭据和脱敏数据，不写入真实身份码、Access Key、签名、鉴权正文、连接凭证或完整配置。
- 格式遵循项目现有工具链的 rustfmt；不为个人排版偏好引入额外格式工具，不混入无关重排。

## 职责与依赖边界

| 位置 | 应放置的代码 | 边界 |
| --- | --- | --- |
| `crates/bridge-core` | 签名、模型、协议解析与序列化、纯策略、恢复状态和生命周期决策 | 不引入 Tokio、HTTP 客户端、系统网络、系统时钟或随机数生成；时间与随机输入由调用方提供 |
| `crates/bridge-native` | 原生网络、任务调度、锁与通知、会话索引、资源名额、配置、日志初始化和可执行入口 | 单向依赖 core，负责执行决策与网络清理；保持现有 `bilibili_live_bridge` 公共路径的兼容性 |
| `crates/bridge-worker` | Worker 入口、Durable Objects、平台网络与存储适配 | 单向依赖 core，不依赖 native；运行时能力与差异见 [Worker 指南](../crates/bridge-worker/README.md) |

- 两端共享的协议和纯决策优先放入 core；运行时特有的调度、资源管理和持久化留在各自适配器。
- 模块按职责拆分，不因文件行数机械拆分，也不为排版增加抽象或执行路径。
- 默认保持私有可见性；只在跨模块或对外使用确有需要时扩大为 `pub(crate)` 或 `pub`。重导出用于组织公开面，不仅为测试暴露内部实现。
- 调整共享模型或策略时同时检查两端调用方；共享协议不表示两端具有相同的恢复、背压或持久化保证。

## Rust 项布局与导入

- 默认通过 `use` 导入类型、trait、函数、常量或模块，避免重复冗长路径。类型与 trait 通常直接导入；函数和常量可保留模块前缀，以来源清晰和局部一致为准。
- 外部 crate 根名可直接用于 `serde_json::from_value`、`tokio::select!` 等，不添加冗余同名导入。类型关联函数、方法与枚举成员保留 `Type::new()`、`value.method()`、`Enum::Variant`。
- 普通导入按标准库（`std/core/alloc`）、其他 crate、本 crate 分组，组间留一行空行。workspace 内的 `bridge_core` 等也属于其他 crate；`crate/self/super` 及本地模块裸路径属于本 crate。组内排序交给 rustfmt，不强制合并或拆分导入树。
- 名称冲突、宏展开、作用域限制或消除歧义需要时，可以保留完整路径；原因不明显时补简短说明。
- 普通实现文件推荐先集中 `use`，再集中生产 `mod` 声明，避免来回交错。crate 根和模块门面可按职责组织模块声明与 `pub use`，不为字母序拆开公开面。
- 类型、类型别名、函数和 `impl` 块之间留一行空行，`impl` 内相邻方法同样如此。文档注释、属性与所属项紧贴；连续导入、模块声明和紧密相关常量可成组。
- 主要入口在前，类型及相关实现就近组织，底层辅助函数在后；不强制类型分类顺序或方法字母序。
- 字段默认连续排列，必要时按语义分组；局部变量按执行阶段分组，不在每个字段或 `let` 之间插空行。
- 宏的文本作用域及其他顺序敏感语义优先保持正确性。不要机械重排宏、字段、枚举变体或执行语句。

导入类型与模块可以混用，例如：

```rust
use std::{fs, io, path::Path};

fn read_sample_config(path: &Path) -> io::Result<String> {
    fs::read_to_string(path)
}
```

此例仅说明导入方式，不改变项目配置的读取方式。

## 方法内分组与异步边界

- 跨多个职责阶段的函数、方法或闭包按语义分组，阶段间留一行空行；相关取值、校验与失败处理就近放置，不按固定行数切块。
- 阶段意图不自明时用一句注释说明目的；策略例外、锁与资源作用域、状态复核等关键边界说明原因或不变量。不要求每组都有注释，不逐句翻译代码。
- 条件复杂时可展开或引入有业务含义的局部变量。分组后仍难以理解的独立职责，再抽取输入输出明确的辅助函数。
- 排版调整必须保持检查顺序、分支、失败处理和资源生命周期。改变锁范围、状态发布顺序或取消行为属于行为修改，需要相应验证。
- 共享状态的临界区尽量短；网络 I/O 在状态锁之外执行，不跨 `await` 持有同步锁或 `RefCell` 借用。确需跨异步操作串行化时，应明确所有者与并发约束。
- 异步操作前后的状态可能变化；按需核对会话身份、代次或关闭状态，防止晚到结果覆盖新状态。一次快照或一次复核不能被注释描述为原子性保证。
- 后台任务必须有明确的所有者、停止条件和清理责任。调用者取消等待、任务取消与远端场次结束是不同事件，不可用直接丢弃任务替代必要的清理。
- 通知只负责唤醒，事实以受保护的状态为准；订阅、关闭和恢复代码应保留防止丢失唤醒、重复清理及旧结果复活的约束，具体规则见架构说明。

## 错误、协议与资源

- 外部输入、网络失败和平台业务失败通过明确的错误类型传播；生产路径不以 `unwrap` / `expect` 处理可预期失败。确有不可违反的不变量时，说明依据。
- 区分输入错误、传输错误、协议或解码错误与平台业务错误；不要用默认成功值掩盖失败，也不要擅自把未知错误归为永久失败。
- 重试由相应策略与运行时统一负责，受截止时间和退避约束；不在低层调用中叠加隐藏重试，不因重试重新开启场次或刷新既有预算。
- 请求正文先序列化，再对同一份正文签名并发送。字段名、单位、缺失值、显式 `null` 和未知命令的处理都属于协议行为，调整时补测试并同步协议文档。
- 保留未知事件、未知业务错误码的兼容路径；不能为适配已知样例而静默丢弃未识别输入。
- 网络输入、解压、缓存、队列、事件日志和并发接入应有明确上限；新增路径应说明超限后的拒绝、丢弃或关闭行为，不引入无界缓冲。
- 保持 ACK、流标识、序号和续传失败的语义；不得在续传失败时静默切换为新流，也不得把内存续传描述为持久化或恰好一次交付。

## 注释与 rustdoc

- 模块顶部用 `//!` 说明职责和外部边界，多个段落之间用空 `//!` 分隔。单文件模块与 `mod.rs` 一致，不写文件内容清单。
- 新增或实质修改的 `pub`、`pub(crate)` 项用 `///` 写中文摘要，句末用句号；公共字段、枚举变体也需说明语义。重导出可复用原项文档，不复制维护同一份说明。
- 协议字段和配置项说明单位、范围、默认值或缺失语义中不自明的部分；枚举变体与常量说明取值边界，不复述类型名称。
- 内部实现用 `//` 解释原因；`unsafe` 块前必须有 `// SAFETY:`，写明依赖的不变量及调用方前提，说明正文使用中文。
- 不机械要求 `# Errors`、`# Panics`、`# Examples`；存在不显然的失败、panic 条件或调用顺序时，用标准 rustdoc 标题补充。行为保证应与实现一致。
- 示例尽量可编译；需要真实网络或凭据的示例使用 `no_run`，不要使用 `ignore` 掩盖失效代码。异步接口说明驱动、取消和清理责任中不显然的部分。

## 测试组织

- 单元测试沿用本项目命名，放在实现旁的 `<module>_test.rs`，通过 `#[cfg(test)]` 与必要的 `#[path = "..."]` 引入；不照搬其他项目的 `*_tests.rs` 命名或新建 `<module>/tests.rs` 层级。
- 普通外置测试模块集中在实现文件末尾，之后不再定义生产项。保留已有路径；`src/bin/` 下的测试文件应放到不会被 Cargo 自动识别为新 binary 的位置。
- 跨公开边界或命令行行为的集成测试放在 crate 的 `tests/`。Worker 的运行时集成测试沿用 `crates/bridge-worker/tests/integration.mjs`。
- 业务文件原则上只保留测试模块引入。测试专用构造器、替身、常量、访问器和日志初始化放入对应测试文件；跨测试复用的辅助放在由 `#[cfg(test)]` 整体门控的测试支持模块。
- 必须访问私有状态、维持类型不变量或控制并发交错且无法移出的最小注入点可以留在业务文件，集中门控并解释原因；不因此扩散测试专用 getter 或扩大公共 API。
- 不为本规范批量迁移已有内联测试。当前没有专门的测试分离检查脚本，代码审查仍需检查测试辅助项的放置。

外置测试模块示例：

```rust
#[cfg(test)]
#[path = "recovery_test.rs"]
mod recovery_test;
```

## 测试质量与验证

- 测试验证可观察行为和关键不变量，覆盖本次修改涉及的成功、失败、边界和回归场景；不只照抄实现分支或断言“没有报错”。
- core 使用显式时间与确定输入验证纯决策；运行时适配器验证网络、任务、通知和清理。共享逻辑测试不能代替 Worker 的 Wasm 编译与运行时测试。
- 并发测试用通知、桩控制入口或暂停时钟推进时序，并设置等待超时；避免用固定 sleep 猜测完成时刻。竞态回归应同时确认交错实际发生和最终输出。
- 默认测试使用假凭据、模拟平台和本地 HTTP / WebSocket 桩，不依赖真实平台。配置通过读取器注入，不修改进程全局环境；日志捕获使用局部 dispatcher，不重复安装全局 subscriber。
- 真实平台联调单独执行并记录范围，不将单次观测写成平台长期保证；本地桩验证和真实平台结论应明确区分。
- 按 [开发指南](development.md) 执行格式、构建、测试与 rustdoc 检查；修改 Worker 时追加该指南的 Workers 验证。只改文档时检查内容、链接和差异，无需运行无关的行为测试。
- 验证结果说明实际执行范围与未验证边界；不能把 native 测试通过等同于两端运行时均已验证。

## 日志与文档同步

- 日志使用稳定的结构化字段，记录动作、资源、错误分类和必要上下文；库不自行安装全局 subscriber，异步任务按现有方式传递日志上下文。
- 不直接记录完整请求、响应、配置、鉴权数据或带凭证的 URL；新增 `Debug`、错误显示和自动请求日志也要检查是否泄露敏感字段。
- 事件正文可能包含弹幕等用户内容，不作为默认运行日志；诊断输出沿用现有级别与过滤边界。
- 新增配置同步解析、校验、默认值、配置模板、README 或 Worker 指南及测试；模板只包含占位值。
- 对外消息或错误语义变化同步 [下游客户端协议](downstream-protocol.md)；生命周期、职责与能力边界变化同步 [架构说明](architecture.md) 和对应运行指南。
- 本文维护编码约定，运行参数和架构细节在对应文档维护，避免复制出多份需要同步的事实。
